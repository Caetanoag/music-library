# AGENTS.md

Browser-only music library app: TypeScript + plain HTML/CSS, Supabase REST backend, built with Bun, deployed to GitHub Pages. No framework, no bundler config beyond `dev/build.ts`.

## Commands

- `bun install` — install dependencies (Bun 1.4.x, lockfile is `bun.lock`).
- `bun run build` — deletes `public/js` and recompiles every file under `src/` into `public/js` with paths preserved.
- `bun run typecheck` — runs `bun check` (TypeScript). There is no test suite or test runner.
- `bunx biome check src dev` — lint + format + import-order check. `bun run format` only rewrites formatting (tabs, double quotes); it does not lint.
- `bun run local-serve` — static server for `public/` on a random port; copies the local URL to the clipboard.
- `bun run serve` — same server, but copies/prints a QR code for the **deployed** GitHub Pages URL; writes `tmpassets/qrcode.png`.
- `bun run deploy` — build, then `serve`, then `format`. `serve` blocks forever, so `format` never actually runs; don't rely on this script in automation.

## Source Layout And Build

- `src/` is the source of truth. `public/js/` is generated by `bun run build` and is also committed, so rebuild after changing `src/` and never hand-edit `public/js/`.
- `public/` is the deployable root. Pages: `public/index.html` (login), `public/html/register.html`, `public/html/my-musics.html`.
- `src/main.ts` is the shared entry imported by the login/register pages; it pulls in all components and auth handlers.
- Components self-register with `customElements.define` and are used as `<music-card>`, `<custom-header>`, `<custom-footer>`.
- Each file under `src/` is its own build entrypoint, so per-file script tags such as `js/components/music-card.js` work. Shared imports are duplicated rather than bundled into one file.
- `src/**` targets the browser (`dev/build.ts` sets `target: "browser"`); keep Node/Bun-specific APIs in `dev/` only.

## Deploy And Paths

- The site is served from the `/music-library/` subpath on GitHub Pages, not the domain root. Use relative URLs in HTML (`css/main.css`, `../js/main.js`), never root-absolute `/...` paths.
- Pushing to `main` runs `.github/workflows/static.yml`: install with frozen lockfile, build, upload `public/` to Pages. No manual deploy step is needed.

## Supabase And Auth

- There is no `supabase-js`; `src/db/auth.ts` and `src/db/music.ts` call Supabase Auth/REST directly via `fetch`. Keep that pattern unless explicitly asked to add the SDK.
- If editing Supabase communication (`src/db/auth.ts`, `src/db/music.ts`, `src/db/supabase.ts`, or related request/response handling), read `src/db/schema.sql` first to understand the database schema.
- Supabase URL and publishable key are hardcoded in `src/db/supabase.ts`. No `.env` loading exists; don't assume environment variables.
- Sessions are stored in `localStorage` under `supabase_session` (access token, refresh token, expiry). `MusicDatabase` reads the access token from there and falls back to the publishable key.
- `music-card` fetches cover/album data from the public iTunes Search API at runtime; failures/empty results are handled by leaving fields blank.

## Git And Commits

- Follow [Conventional Commits](https://www.conventionalcommits.org/) for commit messages (e.g. `feat: ...`, `fix: ...`, `docs: ...`, `chore: ...`).
- Before creating any commit, run `bun run build && bun run format`.
- Before creating any commit, check the local git config: run `git config --local user.name` (or `git config user.name`).
- Only create a commit if the resolved `user.name` is exactly `caetano`.
- If `user.name` is not `caetano`, **do not commit**. Refuse the commit and inform the user that human intervention is required to set the correct local git identity.
